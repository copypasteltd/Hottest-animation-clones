# 产品需求 · 整段视频双角色动作迁移

需求基线 v0.7。首版任务入口为会话，客户在会话里提供 Bilibili、X 或抖音作品链接。每条消息中的链接默认开一个有独立编号的批次。客户明确要求追加时并入指定批次。每条链接选中的完整参考视频在同一批次安排两版，产出两份 S02 基准白模 MP4。单人视频分别用 SA02 与 BM01 替换。双人视频的两份输出均使用 SA02 与 BM01，第二份互换两位表演者对应的角色。[当前进度](<status.md>)

## 五步需求

| 需求 | 项目负责 | 交接结果 |
| --- | --- | --- |
| R-01 | 通过 `/ra-video-download` 下载链接选中的完整参考视频。 | 已完成下载核验的原片和私有来源记录，或可定位的下载结果与原因。 |
| R-02 | 对整条原片判断半身／全身、单人／多人和姿态。 | 整片的取景、人数、姿态和选用理由。 |
| R-03 | 按取景、人数和姿态匹配 S02 替换图。双人以客户指定的身份对应为准，未指定时随机分配第一版，第二版交叉互换。 | 两个版本各自的目标图及人物绑定。 |
| R-04 | 用同一条完整原片和各自的目标图准备两版。两版都就绪时同批提交到指定 RTX 4090 的 ComfyUI 队列。H3 跟随原片运镜。多条原片按同一版本、每组两条入队。组内下载尚在进行时等待，另一条失败或阻塞后，已就绪的原片可单独入队。 | 每版的工作流、运行输入、提交回执和实际状态。 |
| R-05 | 每次生成有结果就反馈。按原回执取回 MP4 后直接交付。 | 每次尝试的结果和对应 MP4，或失败原因。 |

## 整片处理与选图

- Bilibili 分 P 和 X 帖中视频的选择用于确定原片。原片确定后，完整文件就是执行输入。工作流负责从原片获得运动与节奏并完成迁移。人工判断只用于选路线。禁止人工拆动作、抽帧标动作或手工指定关键动作。
- 同时适合半身和全身时优先保证主要动作易读。上身和手势为主用半身。脚步、接地、转身或位移也决定表演时用全身。人数按实际参与表演者计算，姿态按整片的表现和可用配置判断。
- 站立单人沿用既有定稿母版。半身使用 SA02 F01 与 BM01 F05，全身使用 SA02 F02 与 BM01 F06。多人先覆盖双人。两位表演者地位相同。双人任务中的 SA02 和 BM01 是两版的记录标签，用来区分两套人物绑定。绑定在整片内保持固定，换位时也沿用原绑定。[S02 与定稿图](<../assets/reference-images.md#target-frames>)
- S02 允许保留直接参与动作的道具。按相应目标图和工作流配置执行。缺少匹配配置时登记受影响的版本与原因。
- 遇到关键可见性不足、身份对应不清、未配置姿态或工作流无法覆盖完整原片时，登记整条视频或受影响版本的原因。禁止将参考视频拆段、剪短或将部分动作作为交付替代。

## 交付与重跑

运行中的批次按原回执取回 MP4 后逐版直接交付。简要说明含源 ID、角色版本、整片输入、实际音轨处理和已知执行限制。重复链接按本次人物绑定及配置复用最近成功取回的结果。用户点名调整或重做时为相应版本另记尝试。工作流支持时，主动重做默认换种子，执行故障补跑优先沿用原种子。[逐次反馈与交付](<../operations/runbook.md#delivery>)

停止当前批次时，按回执处理全部未完成任务。已经生成、尚未取回的版本先反馈结果，并在批次恢复时按原回执取回。继续一个批次时，默认恢复全部剩余任务。会话意外中断后，核对原回执并逐条补发尚未反馈的结果。原片、实际执行图、回执和成片按批次长期保留。[排队与恢复](<../operations/h3-4090.md#queue-and-stop>) · [项目留存](<../maintenance/workspace.md#retention>)
